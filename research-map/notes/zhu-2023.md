## 2026-11-08 · Summary
Converts a whole IFC file into a labeled property graph in neo4j, called IFC-Graph, with no user choice of what to keep.
Every IFC instance becomes a node, literal attributes become properties, entity and inverse attributes become edges, and
the class with all its parents becomes the labels. Validated on 8 IFC models: four from KIT, two bridges marked "Project",
one from the Open IFC Model Repository and the Revit sample. The aim is querying IFC with Cypher outside AEC. It does not
learn or generate anything.

Results
- Completeness: in all 8 models the number of IFC instances equals the number of nodes with a numeric id, and the number
  of IFC classes equals the number of labels (Table 6). Example: Institute, 147,712 instances and 189 classes.
- Size: 194,845 nodes and 285,504 relationships (Institute); 537,219 nodes and 924,740 relationships (Revit sample).
- Generation time: 133,604 s for the Revit sample, 28,824 s for Hospital Parking, 25 s for Bridge 1 (Table 7).
- File size against IFC-SPF, on average: ifcXML 849%, ifcOWL 671%, IFC-Graph 303%.
- IfcOwnerHistory is linked only to IfcProject. Linked from every IfcRoot instance, one query on it returns 1304 records.

For the thesis
- A lossless baseline: Hornung et al. keep six classes, this keeps every instance. It is the reference for measuring what a
  smaller graph throws away, and its completeness test (instance count, class count) is cheap to copy.
- It does not decompose: the output is the whole file as one graph, with no parts and no cut.
- Nothing goes back: no IFC or Revit is written from the graph, so no round trip and no validity check.
- The authors doubt their own full graph: geometry points inflate it and ordered lists (points of a polyloop) are not kept.
- Processing time grows quickly with nodes; they suggest stable uses such as operation and maintenance.
- Input is IFC, not a Revit data lake. Eight models, mostly samples, one graph per model; no split by project.

Doubts from reading it (Claude's, not the paper's)
- "Full conversion" is shown for instance and class counts only. Table 5 shows one outgoing relationship fewer than
  attributes for four of five instances (the omitted OwnerHistory edge). Edges and values are checked by hand on five instances.
- Resource instances without an id (IfcLabel, IfcDate) get an arbitrary text id "to avoid creating duplicated nodes", so
  equal values may merge. The check counts them apart (nodes with text id), so it cannot see this.
